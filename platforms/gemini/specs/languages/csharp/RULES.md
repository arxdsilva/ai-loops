# C# (.NET) rules

The citable rule book for C# backend code in a loops run: the `csharp` language pack. Written against .NET 10 LTS and C# 14, as of 2026-11 (.NET 8 and .NET 9 leave support 2026-11-10; .NET 11 reaches GA this month). Source: `research/languages/csharp.md` (rule IDs kept). Cite by ID (`CS-CONC-05`).

- Project rules win: follow the repo's own `.editorconfig`, analyzer severities, test framework and `global.json` over these defaults, and log every override with `loops run override` (ROLES.md "Project rules first").
- Universal rules are not repeated here: layering, ports and SOLID live in `specs/ARCHITECTURE.md` and `specs/SOLID.md`. The rules below add only what is .NET-specific.
- Tool commands, the race policy and the coverage recipe are in `specs/languages/csharp/pack.json`; `loops gate` runs them.

## REPO: repository and project management

- **`CS-REPO-01`** (SHOULD) Put production code under `src/`, tests under `tests/`, one project per hexagon layer or bounded module, and keep `.sln`/`.slnx` at the repo root. The solution is the unit `dotnet build/test` operate on; a stable tree lets globs identify source vs test. ([MS: .NET project SDK overview](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/overview))
- **`CS-REPO-02`** (SHOULD) Use a single solution for a service or monorepo; prefer `.slnx` (XML, SDK 9.0.200+, default `dotnet new sln` in the .NET 10 SDK) over legacy `.sln`; keep one `.sln(x)` per deployable group, not one per project. `.slnx` is mergeable and readable; `dotnet build/test` fail on a folder with several solutions. ([.NET blog: slnx support in dotnet CLI](https://devblogs.microsoft.com/dotnet/introducing-slnx-support-dotnet-cli/))
- **`CS-REPO-03`** (SHOULD) Bootstrap with `dotnet new` templates (`sln`, `classlib`, `webapi`, `worker`, `mstest`/`nunit`, `globaljson`, `editorconfig`, `gitignore`, `packagesprops`, `buildprops`) instead of hand-written csproj. Templates carry current SDK defaults and avoid copy-paste drift. ([MS: dotnet new templates](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-new-sdk-templates))
- **`CS-REPO-04`** (MUST) A day-one repo MUST contain `global.json`, `Directory.Build.props`, `Directory.Packages.props`, `.editorconfig`, `.gitignore` (`dotnet new gitignore`), `nuget.config`, a LICENSE, and a CI workflow that runs build, test and `dotnet package list --vulnerable`. These files define reproducibility, style and supply-chain policy before the first commit. ([MS: customize your build by directory](https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory))
- **`CS-REPO-05`** (MUST) Adopt Central Package Management: `Directory.Packages.props` with `<ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>`, `<PackageVersion>` items there, and version-less `<PackageReference>` in projects. Allow `VersionOverride` only with a comment; consider `CentralPackageVersionOverrideEnabled=false`. One place to review and bump versions; Renovate/Dependabot diffs become one file. ([MS: Central Package Management](https://learn.microsoft.com/en-us/nuget/consume-packages/central-package-management))
- **`CS-REPO-06`** (SHOULD) Set `<CentralPackageTransitivePinningEnabled>true</CentralPackageTransitivePinningEnabled>` in applications to pin a vulnerable transitive package without a top-level reference; avoid it in libraries (it promotes pins to the nuspec). Fixes transitive CVEs; NuGet rejects downgrades (NU1109). ([MS: CPM transitive pinning](https://learn.microsoft.com/en-us/nuget/consume-packages/central-package-management))
- **`CS-REPO-07`** (SHOULD) Commit `packages.lock.json` for applications (`<RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>` in `Directory.Build.props`) and restore in CI with `dotnet restore --locked-mode`; do NOT commit lock files for libraries. When using lock files set `rollForward` to `disable` in `global.json` so implicit SDK packages do not change the graph. Repeatable restores; floating or newly published versions cannot change a build silently. ([MS: NuGet lock files](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files))
- **`CS-REPO-08`** (MUST) Configure `nuget.config` with `<packageSourceMapping>` so each package id maps to one feed (private feed or nuget.org); never leave several unmapped sources (NU1507 under CPM). Blocks dependency-confusion attacks and ambiguous resolution. ([MS: package source mapping](https://learn.microsoft.com/en-us/nuget/consume-packages/package-source-mapping))
- **`CS-REPO-09`** (SHOULD) Enable automated updates with Renovate (`nuget` manager) or Dependabot (`package-ecosystem: nuget`, which understands CPM and `global.json`); group `Microsoft.*`/`Microsoft.Extensions.*` bumps by the .NET major. Keeps framework packages aligned with the SDK; unattended CVE fixes. ([Dependabot supported ecosystems](https://docs.github.com/en/code-security/dependabot/ecosystems-supported-by-dependabot/supported-ecosystems-and-repositories))
- **`CS-REPO-10`** (SHOULD) Version with SemVer in the project (`<Version>` or `VersionPrefix`/`VersionSuffix`) or derive it from git tags with Nerdbank.GitVersioning; publish with `dotnet pack -c Release` then `dotnet nuget push` using an API key from CI secrets; enable `<ContinuousIntegrationBuild>true</ContinuousIntegrationBuild>`, `<Deterministic>true</Deterministic>`, SourceLink and symbol packages (`.snupkg`) in CI. Reproducible, debuggable, signable packages. ([MS: dotnet pack](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-pack))
- **`CS-REPO-11`** (MUST) Pin the SDK in `global.json` with a full version and `rollForward` of `latestFeature` (or `disable` with lock files): `{"sdk":{"version":"10.0.100","rollForward":"latestFeature"}}`; the version field takes no wildcards. Developers and CI use the same compiler/analyzers; unpinned CI follows the newest installed SDK including previews. ([MS: global.json](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json))
- **`CS-REPO-12`** (MUST) Put cross-cutting MSBuild settings (`TargetFramework`, `Nullable`, `ImplicitUsings`, `LangVersion`, `AnalysisLevel`, `TreatWarningsAsErrors`, `EnforceCodeStyleInBuild`, `RestorePackagesWithLockFile`) in `Directory.Build.props` at the repo root; only the nearest file is auto-imported, so import the parent explicitly in nested ones. One policy for all projects; no per-csproj drift. ([MS: customize by directory](https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory))
- **`CS-REPO-13`** (MUST) Commit `.editorconfig` with `root = true`, naming rules and analyzer severities, plus `.gitattributes` (`* text=auto eol=lf`, `*.sln text eol=crlf` only if needed). Generate with `dotnet new editorconfig`. `dotnet format`, the IDE and CI read the same rules; line-ending churn is removed. ([MS: EditorConfig for code analysis](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/configuration-files))
- **`CS-REPO-14`** (SHOULD) CI stages: `dotnet restore --locked-mode` → `dotnet format --verify-no-changes` → `dotnet build -warnaserror` → `dotnet test` with Cobertura → `dotnet package list --vulnerable --include-transitive` → `dotnet publish`/container; cache `~/.nuget/packages` keyed on `**/packages.lock.json` or `Directory.Packages.props`; matrix over OS and supported TFMs for libraries. Fails fast on cheap checks; the cache avoids re-downloading the world. ([GitHub: setup-dotnet caching](https://github.com/actions/setup-dotnet#caching-nuget-packages))
- **`CS-REPO-15`** (SHOULD) Use conventional commits and generate release notes from them (GitHub release notes or `git-cliff`); tag releases `vX.Y.Z`. Language-neutral; matches loops release flow. ([Conventional Commits 1.0](https://www.conventionalcommits.org/en/v1.0.0/))

## TOOL: toolchain

- **`CS-TOOL-01`** (MUST) Target the current LTS (`net10.0`) for new services; as of 2026-11: .NET 10 LTS supported to 2028-11-14, .NET 8 LTS and .NET 9 STS end 2026-11-10, .NET 11 (STS, 24 months) reaches GA this month. LTS = 3 years, STS = 24 months since .NET 9; a new major ships every November. Install SDKs with the official installer, `dotnet-install.sh` or `actions/setup-dotnet` reading `global.json`. Avoids an unsupported runtime in production; no version manager is needed since `global.json` selects side-by-side SDKs. ([.NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core))
- **`CS-TOOL-02`** (MUST) Format with `dotnet format` driven by `.editorconfig`; CI check argv: `dotnet format --verify-no-changes` (non-zero exit if anything would change); scope with `--include <paths>`, split with subcommands `whitespace`, `style`, `analyzers`; `--severity` defaults to `warn`. The one built-in formatter; no separate config file. ([MS: dotnet format](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-format))
- **`CS-TOOL-03`** (MUST) Enable the built-in .NET analyzers: `<AnalysisLevel>latest-recommended</AnalysisLevel>` (or `latest-all` for greenfield), `<EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>`, `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` (at least in CI via `-warnaserror`); tune per rule with `dotnet_diagnostic.CAxxxx.severity` in `.editorconfig`. Analyzers run inside `dotnet build`, so no extra gate command is needed. ([MS: .NET code analysis overview](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/overview))
- **`CS-TOOL-04`** (SHOULD) Add third-party analyzers as `PrivateAssets=all` global package references in `Directory.Packages.props` (`<GlobalPackageReference>`): StyleCop.Analyzers (style, SA rules), Meziantou.Analyzer, optionally SonarAnalyzer.CSharp or Roslynator; configure SA rules in `.editorconfig`, disable file-header rules you do not use. Catches API, async and security smells beyond the SDK set; global refs apply to every project. ([StyleCopAnalyzers](https://github.com/DotNetAnalyzers/StyleCopAnalyzers))
- **`CS-TOOL-05`** (MUST) Enable nullable reference types for every project (`<Nullable>enable</Nullable>`), and treat CS8600-CS8625 as errors (`<WarningsAsErrors>nullable</WarningsAsErrors>`); do not sprinkle `!`. The compiler is the type checker for null; warnings left on rot. ([MS: nullable reference types](https://learn.microsoft.com/en-us/dotnet/csharp/nullable-references))
- **`CS-TOOL-06`** (MUST) Scan dependencies in CI with `dotnet package list --vulnerable --include-transitive` (SDK 10; `dotnet list package ...` on SDK 9 and earlier), and also let NuGetAudit fail restore: `<NuGetAudit>true</NuGetAudit>`, `<NuGetAuditMode>all</NuGetAuditMode>`, `<NuGetAuditLevel>low</NuGetAuditLevel>`, `<WarningsAsErrors>$(WarningsAsErrors);NU1901;NU1902;NU1903;NU1904</WarningsAsErrors>`. The list command exits 0 even when it reports vulnerabilities, so parse the output (`--format json`). NuGetAudit is on by default (warnings); making NU190x errors is what makes it a gate. ([MS: dotnet package list](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-list))
- **`CS-TOOL-07`** (SHOULD) Generate an SBOM (`CycloneDX` .NET tool, `dotnet tool install --global CycloneDX`, or `Microsoft.Sbom.DotNetTool`) in release builds and run a license check on it; keep tools in a `dotnet-tools.json` manifest (`dotnet new tool-manifest`, `dotnet tool restore`). Reproducible local tools and release provenance. ([MS: dotnet tool install](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-tool-install))
- **`CS-TOOL-08`** (AVOID) Do not enable editor format-on-save unless the editor reads the same `.editorconfig` as `dotnet format` (C# Dev Kit, `csharp-ls`, `roslyn-language-server`, VS or Rider all can); set `"editor.formatOnSave"` only if the IDE reads the same `.editorconfig`. Editor and CI formatters disagree when config differs. ([C# Dev Kit](https://code.visualstudio.com/docs/csharp/get-started))

## ARCH: architecture

- **`CS-ARCH-01`** (MUST) Map the hexagon to projects: Domain (no `PackageReference`, no `ProjectReference`), Application (-> Domain), Infrastructure (-> Application), host (-> both). Never add a reference from Domain or Application to Infrastructure or to `Microsoft.AspNetCore.*`/`Microsoft.EntityFrameworkCore`. A project reference cannot be violated by accident; the compiler rejects the `using`. ([MS: common web application architectures (clean architecture)](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures))
- **`CS-ARCH-02`** (MUST) Inside a project, namespace = folder path = `<Assembly>.<Folder>`. Layers are resolved from `<ProjectReference>` items in `*.csproj` (and `Directory.Build.props`), not from `using` strings alone; `loops arch` reads the project graph (`arch.resolver = project-reference`). Namespaces are not tied to directories by the compiler, and a `using` shows a namespace, not an assembly. ([MS: namespaces](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/types/namespaces))
- **`CS-ARCH-03`** (SHOULD) Use access modifiers as the module boundary: types `internal` by default, `public` only for the project's API; expose internals to the test project with `<InternalsVisibleTo Include="Shop.Domain.Tests"/>` in the csproj, never to other production projects. Cyclic project references are rejected by MSBuild; cyclic namespaces inside an assembly are allowed and must be checked by tests. `internal` is assembly-level encapsulation. ([MS: access modifiers](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/access-modifiers))
- **`CS-ARCH-04`** (MUST) Enforce dependency direction with an architecture test project: NetArchTest.Rules (`Types.InAssembly(typeof(X).Assembly).That().ResideInNamespace("Shop.Domain").ShouldNot().HaveDependencyOn("Shop.Infrastructure").GetResult().IsSuccessful`) or ArchUnitNET (`Types().That().ResideInAssembly(domain).Should().NotDependOnAny(infra).Check(arch)`); also assert no cycles and that handlers end with `Handler`. Run it in `dotnet test`. Catches `using` leaks within one assembly and keeps rules in code review. ([NetArchTest.Rules](https://www.nuget.org/packages/NetArchTest.Rules))
- **`CS-ARCH-05`** (MUST) Compose dependencies only in the host's `Program.cs` (generic host/`WebApplication.CreateBuilder`); register with `AddScoped/AddSingleton/AddTransient` in per-project `AddShopApplication(this IServiceCollection)` extension methods, and enable `ValidateScopes` and `ValidateOnBuild` in Development. Single composition root; scope validation catches captive dependencies. ([MS: DI guidelines](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/guidelines))
- **`CS-ARCH-06`** (AVOID) Use constructor injection only; no service locator (`IServiceProvider.GetService` outside the composition root or factories), no static singletons, no `[FromServices]` property injection in domain code; do not inject `IServiceProvider` into handlers. Hidden dependencies break tests and the arch rule. ([MS: DI guidelines](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/guidelines))
- **`CS-ARCH-07`** (MUST) Keep Domain pure: no `DateTime.Now/UtcNow`, `DateTimeOffset.UtcNow`, `Guid.NewGuid()`, `Random`, `Environment.*`, `System.IO`, `System.Net.Http`, `System.Data`, `Microsoft.EntityFrameworkCore`, logging or `[JsonProperty]` attributes. Inject `TimeProvider` (BCL, .NET 8+; `FakeTimeProvider` in `Microsoft.Extensions.TimeProvider.Testing`), an `IIdGenerator` and `Random` as ports. Determinism and testability; time is a port. ([MS: TimeProvider](https://learn.microsoft.com/en-us/dotnet/api/system.timeprovider))
- **`CS-ARCH-08`** (SHOULD) Define ports as small interfaces in the Application project (consumer-owned), named by role (`IOrderRepository`, `IPaymentGateway`), with implementations `internal sealed` in Infrastructure registered via extension methods; avoid a shared `IRepository<T>` generic CRUD abstraction over `DbContext`. EF Core's `DbSet` is already a repository/unit-of-work; thin role interfaces keep ports small. ([MS: infrastructure persistence layer design](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/infrastructure-persistence-layer-design))
- **`CS-ARCH-09`** (SHOULD) Apply SOLID with .NET size heuristics: classes under ~300 lines, methods under ~40 lines, at most 4-5 constructor parameters (more means split the class), `sealed` classes by default, interfaces under ~5 members. Heuristics only; project rules win. ([MS: framework design guidelines](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/))
- **`CS-ARCH-10`** (SHOULD) Model aggregates with private setters, factory methods and invariants in the constructor; value objects as `readonly record struct` or `sealed record`; raise domain events from the aggregate (list of `IDomainEvent`) and dispatch them in the unit of work after commit. DDD tactical patterns map directly onto records and EF Core owned types. ([MS: DDD-oriented microservice domain model](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/microservice-domain-model))
- **`CS-ARCH-11`** (SHOULD) In a modular monolith, give each module its own projects and DbContext/schema, expose only a `Contracts` project (interfaces, DTOs, integration events) to other modules, and test the rule with NetArchTest. Prevents the monolith from becoming a big ball of mud; keeps the split option open. ([MS: common web application architectures](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures))

## IDIOM: what to do and what to avoid

- **`CS-IDIOM-01`** (MUST) Use exceptions for exceptional failures and `Result<T>`/discriminated-union style returns (or `bool TryXxx(out ...)`) for expected domain failures; throw the most specific type, derive custom exceptions from `Exception` (not `ApplicationException`), never `catch (Exception)` without rethrow/log, rethrow with `throw;` (never `throw ex;`), and never use exceptions for control flow. `throw ex` resets the stack trace; broad catches hide defects. ([MS: exception design guidelines](https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/exceptions))
- **`CS-IDIOM-02`** (SHOULD) Validate arguments with `ArgumentNullException.ThrowIfNull(x)`, `ArgumentException.ThrowIfNullOrEmpty`, `ArgumentOutOfRangeException.ThrowIfNegative` at public API entry; never return `null` for collections (return empty) and prefer `Try` patterns over null for optional results. Throw helpers are cheaper and give the right parameter name. ([MS: ArgumentNullException.ThrowIfNull](https://learn.microsoft.com/en-us/dotnet/api/system.argumentnullexception.throwifnull))
- **`CS-IDIOM-03`** (MUST) With `<Nullable>enable</Nullable>`: annotate honestly (`string?`), use `required` members and constructor init instead of `null!`, use `[NotNullWhen]`/`[MaybeNullWhen]` on `Try` methods, and never silence with `!` unless an invariant is proven in a comment. In EF entities, use `required` or `= null!` only on navigation properties EF fills. A lie in annotations propagates NullReferenceException to runtime. ([MS: nullable reference types](https://learn.microsoft.com/en-us/dotnet/csharp/nullable-references))
- **`CS-IDIOM-04`** (SHOULD) Model data with `record` (reference, value equality, `with`) and `readonly record struct` for small immutables; use `init`-only properties and `required` for DTOs; collections exposed as `IReadOnlyList<T>`/`IReadOnlyCollection<T>` or `ImmutableArray<T>`. Do not make mutable `class` entities `record`s (EF identity/tracking relies on reference equality). Records give structural equality for free; EF entities need reference identity. ([MS: records](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/record))
- **`CS-IDIOM-05`** (SHOULD) Use pattern matching and switch expressions (`x switch { ... }`, `is not null`, property/list/relational patterns) and keep switch expressions exhaustive (CS8509 as error); model closed hierarchies with `sealed` records and a private-constructor base, until C# union types ship (preview in C# 15 as of 2026-11). Use `enum` with `[Flags]` carefully and validate with `Enum.IsDefined`. Exhaustiveness checking replaces visitor boilerplate; enum values can hold any int. ([MS: pattern matching](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/functional/pattern-matching))
- **`CS-IDIOM-06`** (MUST) Dispose everything `IDisposable`/`IAsyncDisposable` with `using var x = ...;` or `await using var x = ...;`; implement `IAsyncDisposable` when the type owns async resources; do not write finalizers unless owning unmanaged handles (use `SafeHandle`); never `using` an `HttpClient` per request (see API-06). Connection, file and handle leaks. ([MS: implementing Dispose](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/implementing-dispose))
- **`CS-IDIOM-07`** (MUST) Override `Equals` and `GetHashCode` together (`HashCode.Combine`), implement `IEquatable<T>` on structs, never use mutable fields in hash codes; compare strings with an explicit `StringComparison` (`Ordinal`/`OrdinalIgnoreCase` for identifiers, `InvariantCulture` for persisted data), use `StringBuilder` in loops, `CultureInfo.InvariantCulture` for parsing/formatting machine data. Culture bugs (Turkish i) and hash-set corruption. ([MS: best practices for strings](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings))
- **`CS-IDIOM-08`** (SHOULD) Store and exchange time as `DateTimeOffset` (UTC) or `DateOnly`/`TimeOnly`/`Instant`; avoid `DateTime` with `Kind=Unspecified`; get "now" only from `TimeProvider.GetUtcNow()`; use IANA zone ids with `TimeZoneInfo` (works cross-platform since .NET 6). DateTime has implicit local-time conversions. ([MS: choosing between DateTime, DateTimeOffset, TimeSpan, TimeZoneInfo](https://learn.microsoft.com/en-us/dotnet/standard/datetime/choosing-between-datetime))
- **`CS-IDIOM-09`** (SHOULD) Follow the .NET naming guidelines: `PascalCase` types/members/namespaces, `camelCase` locals/parameters, `_camelCase` private fields, `I` prefix for interfaces, `Async` suffix on Task-returning methods, no Hungarian; use file-scoped namespaces and `var` when the type is apparent; write XML doc comments (`///` with `<summary>`) on public API and generate the doc file (`GenerateDocumentationFile`). Official conventions; IDE0xxx rules enforce most via `.editorconfig`. ([MS: C# identifier names](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/coding-style/identifier-names))
- **`CS-IDIOM-10`** (SHOULD) Avoid reflection, `dynamic`, `Activator.CreateInstance` and runtime codegen in business code; prefer source generators (`System.Text.Json` source gen, `LoggerMessage`, `GeneratedRegex`, `Mapperly`) which are trimming/AOT-safe; reflection acceptable in composition-root scanning (Scrutor) and test helpers only. AOT/trimming and speed; reflection hides dependencies from the arch checker. ([MS: source generators overview](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/source-generators-overview))
- **`CS-IDIOM-11`** (SHOULD) Use LINQ for clarity but never materialize twice: avoid multiple enumeration of `IEnumerable<T>` (CA1851), `Count()` on `IEnumerable` when `Any()` or a property suffices, and `ToList()` inside loops; use `FrozenDictionary`/`ImmutableArray` for read-mostly lookups. Multiple enumeration re-runs side effects and queries. ([CA1851](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca1851))

## CONC: concurrency and the `-race` equivalent

- **`CS-CONC-01`** (MUST) Treat `async`/`await` on the thread pool as the default model (Tasks, `ValueTask`, `Channel<T>`, `IAsyncEnumerable<T>`); use `Task.Run` only for CPU-bound work off a request thread, never to wrap I/O. ASP.NET Core has no `SynchronizationContext`, so `ConfigureAwait(false)` is needed in libraries only. The thread pool is small and shared; blocking it starves the host. ([MS: ASP.NET Core best practices](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/best-practices))
- **`CS-CONC-02`** (MUST) Share state with immutable types, `Interlocked`, `lock` on a private `object` (use `System.Threading.Lock` in C# 13+/.NET 9+), `SemaphoreSlim.WaitAsync` for async critical sections (never `lock` around `await`), `ConcurrentDictionary` (beware `GetOrAdd` factory running more than once) and `Channel<T>` for producer/consumer. Never lock on `this`, a `Type` or a string. Prevents data races and deadlocks; async code cannot hold a `lock` across `await`. ([MS: managed threading best practices](https://learn.microsoft.com/en-us/dotnet/standard/threading/managed-threading-best-practices))
- **`CS-CONC-03`** (SHOULD) Do not rely on a detector: run concurrency tests under stress (many iterations, `Parallel.For`, `Task.WhenAll`), optionally with a deterministic scheduler such as Microsoft Coyote for systematic testing, and keep xUnit's default parallel collections. No TSan for managed code; Coyote explores task interleavings. ([xunit: running tests in parallel](https://xunit.net/docs/running-tests-in-parallel))
- **`CS-CONC-04`** (MUST) Race policy (WORKFLOW §6): .NET has no race detector, so the pack declares `race.mode = none` with the substitute checks `test` (xUnit parallel collections on), `concurrency-repeat` (tests tagged `Category=Concurrency`, run 3 times) and `build` (concurrency analyzers as errors). Never add a fake `-race` flag to `dotnet test`. An honest "no equivalent" plus required substitute checks beats a flag that does nothing. ([xunit parallelism](https://xunit.net/docs/running-tests-in-parallel))
- **`CS-CONC-05`** (MUST) Never block on async: no `.Result`, `.Wait()`, `.GetAwaiter().GetResult()` or `Task.WaitAll` in request paths (sync-over-async deadlocks and starves the pool); never `async void` except event handlers; always `await` or return the Task (CS4014/CA2007/CA2012); do not `await` a `ValueTask` twice or use `.Result` on an incomplete one. The top ASP.NET Core performance and reliability bugs. ([MS: ASP.NET Core best practices](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/best-practices))
- **`CS-CONC-06`** (SHOULD) Use `ConfigureAwait(false)` in library code that may run under a `SynchronizationContext` (WPF, legacy ASP.NET); in ASP.NET Core application code omit it; enable CA2007 only in library projects. Avoids context deadlocks without noise. ([MS: ConfigureAwait FAQ (blog)](https://devblogs.microsoft.com/dotnet/configureawait-faq/))
- **`CS-CONC-07`** (MUST) Pass a `CancellationToken` as the last parameter through every async call chain (`HttpContext.RequestAborted`, `IHostApplicationLifetime.ApplicationStopping`), use `CancellationTokenSource.CreateLinkedTokenSource` and `CancelAfter` for timeouts, and do not swallow `OperationCanceledException`. (CA2016.). Cancellation is cooperative; ignoring it leaks work after client disconnects. ([MS: CA2016](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/quality-rules/ca2016))
- **`CS-CONC-08`** (MUST) Run background work in `BackgroundService`/`IHostedService` (override `ExecuteAsync`, honour `stoppingToken`, catch exceptions inside the loop because an unhandled one stops the host by default), use `Channel<T>` for in-process queues, a durable queue/Hangfire/Quartz/Wolverine for jobs; set `HostOptions.ShutdownTimeout` to cover in-flight work. Do not fire-and-forget `Task.Run` in request handlers. Unobserved task exceptions and lost work on shutdown. ([MS: worker services](https://learn.microsoft.com/en-us/dotnet/core/extensions/workers))
- **`CS-CONC-09`** (AVOID) Use `ValueTask`/`ValueTask<T>` only for measured hot paths that usually complete synchronously; consume it exactly once, never store or `await` it multiple times, and convert with `.AsTask()` if you must. Default to `Task`. ValueTask misuse produces undefined behaviour. ([MS: ValueTask](https://learn.microsoft.com/en-us/dotnet/api/system.threading.tasks.valuetask-1))

## TEST: testing

- **`CS-TEST-01`** (SHOULD) Use xUnit.net as the default unit framework: v3 (`dotnet new install xunit.v3.templates` then `dotnet new xunit3 -f net10.0`; package `xunit.v3`, MTP-native, so use the MTP coverage variant) for new projects, or v2 (`dotnet new xunit`, xunit 2.9.x + coverlet.collector + VSTest) in existing ones; NUnit and MSTest are acceptable if the repo already uses them; TUnit is MTP-only and source-generated. Keep unit, integration and architecture tests in separate projects. xUnit is the de-facto choice in ASP.NET Core docs and templates; MTP is the future runner for all of them. ([xunit.net](https://xunit.net/))
- **`CS-TEST-02`** (SHOULD) Name test projects `<Project>.Tests` / `<Project>.IntegrationTests`, mirror the source folder layout, one test class per class under test, files `*Tests.cs`; test methods `Method_Scenario_Expected` or descriptive sentences. The test-file globs are `**/*Tests.cs`, `**/*Test.cs`, `tests/**/*.cs`, `**/*.Tests/**/*.cs`; a project is a test project when its csproj references `Microsoft.NET.Test.Sdk`, `xunit.v3`/`xunit`, `NUnit` or `MSTest`, or sets `<IsTestProject>true`. The recogniser for "tests exist for new code". ([MS: unit testing best practices](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices))
- **`CS-TEST-03`** (SHOULD) Write arrange-act-assert tests; use `[Theory]` with `[InlineData]`, `[MemberData]` or `[ClassData]` for table-driven cases; share expensive setup with `IClassFixture<T>`/`ICollectionFixture<T>` (xUnit creates a new class instance per test); no logic or loops in tests. Readable failures; isolation by default. ([xunit: shared context](https://xunit.net/docs/shared-context))
- **`CS-TEST-04`** (SHOULD) Prefer hand-written fakes and in-memory implementations of ports; use NSubstitute or Moq (note the Moq 4.20 SponsorLink controversy: pin or prefer NSubstitute/FakeItEasy) for interaction checks only; mock only ports you own, never `DbContext`, `HttpClient` internals or the BCL (use `HttpMessageHandler` fakes, `FakeTimeProvider`). Assertion library: xUnit asserts or Shouldly (FluentAssertions v8+ is commercial). Over-mocking couples tests to implementation; licensing changes affect CI. ([NSubstitute](https://github.com/nsubstitute/NSubstitute))
- **`CS-TEST-05`** (MUST) Run integration tests against the real stack: `WebApplicationFactory<Program>` (make `Program` visible with `public partial class Program {}`), real database via Testcontainers for .NET (`PostgreSqlBuilder`, `MsSqlBuilder`), `Respawn` or transaction rollback to reset between tests; do not test EF Core against the InMemory provider. InMemory/SQLite differ from production SQL semantics. ([MS: integration tests in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/test/integration-tests))
- **`CS-TEST-06`** (MUST) Collect coverage as Cobertura: VSTest `dotnet test --collect:"XPlat Code Coverage" --results-directory <dir>` (add `-- DataCollectionRunSettings.DataCollectors.DataCollector.Configuration.Format=cobertura,lcov` to pick formats; the collector's name is case-insensitive) or MTP `dotnet test --coverage --coverage-output-format cobertura` (no fixed `--coverage-output`, see CS-TEST-07) with `Microsoft.Testing.Extensions.CodeCoverage`; coverlet.MTP alternative: `dotnet test --coverlet --coverlet-output-format cobertura` (writes `coverage.json` by default in the current directory). Both report line and branch coverage. Cobertura is the common denominator for diff-cover, ReportGenerator and CI. ([MS: code coverage for unit testing](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-code-coverage))
- **`CS-TEST-07`** (MUST) In multi-project solutions, never pass one fixed `--coverage-output` (relative, or absolute, which bypasses the per-module directories) to several test projects (they overwrite each other silently with the default flat layout); omit it (GUID names; the pack's `mtp` variant does this and globs `{coverage_dir}/**/*cobertura.xml`) or use `--results-directory-layout per-module` (SDK 10.0.402+/11), then merge with ReportGenerator `reportgenerator -reports:"**/coverage.cobertura.xml" -targetdir:cov -reporttypes:Cobertura`. Silent loss of coverage data is documented MTP behaviour. ([MS: coverage output files](https://learn.microsoft.com/en-us/dotnet/core/testing/microsoft-testing-platform-code-coverage))
- **`CS-TEST-08`** (SHOULD) Exclude generated code from coverage: coverlet defaults skip `[GeneratedCode]`, `[CompilerGenerated]` and `[ExcludeFromCodeCoverage]` members; add `ExcludeByFile` globs for `**/Migrations/*.cs`, `**/*.g.cs`, `**/*.Designer.cs`; the Microsoft collector excludes test assemblies by default (`IncludeTestAssembly=false`). Generated and migration code distorts the percentage. ([coverlet](https://github.com/coverlet-coverage/coverlet))
- **`CS-TEST-09`** (MUST) New-code coverage is at least 70%, computed by `loops gate` from the Cobertura per-line `hits` intersected with the changed lines (no diff-cover needed). Native tools report only total coverage; the diff is the gate's job. ([diff_cover](https://github.com/Bachmann1234/diff_cover))
- **`CS-TEST-10`** (SHOULD) Use property-based tests (FsCheck with xUnit, or CsCheck) for parsers, serializers and invariants, and Stryker.NET mutation testing (`dotnet stryker`) on the Domain project, run nightly rather than per PR. Finds edge cases and weak tests; mutation runs are slow. ([FsCheck](https://github.com/FsCheck/FsCheck))
- **`CS-TEST-11`** (MUST) Keep tests deterministic: inject `TimeProvider`/`FakeTimeProvider`, seeded `Random`, no `Thread.Sleep` (await conditions or use fakes), no shared static state, no dependence on test order; configure xUnit parallelism explicitly (xunit.v3 4.x: `[assembly: Parallelization(MaxThreads = n, Mode = ...)]`; v2 and v3 before 4.0: `[assembly: CollectionBehavior(...)]`, `xunit.runner.json` `maxParallelThreads`) and put tests sharing a resource in one `[Collection]`. Flaky tests are mostly shared state or time. ([xunit: parallelism](https://xunit.net/docs/running-tests-in-parallel))
- **`CS-TEST-12`** (SHOULD) For the TDD loop use `dotnet watch test`, `dotnet test --filter "FullyQualifiedName~OrderTests"` (VSTest) or `dotnet test --filter-method`/`--filter-class` style MTP filters via `--` for xUnit v3, `--no-build` after a build, and `--minimum-expected-tests N` so a silently empty run fails (exit code 8/9). Fast feedback; zero-test runs are otherwise green. ([MS: dotnet test with MTP](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-test-mtp))

## PERF: performance and profiling

- **`CS-PERF-01`** (SHOULD) Benchmark with BenchmarkDotNet in a `benchmarks/` console project run in Release (`dotnet run -c Release --project benchmarks/... -- --filter *Name*`), with `[MemoryDiagnoser]`; compare runs with `--exporters json` and the `BenchmarkDotNet.Tool` compare or `--baseline`. Never benchmark in Debug. BDN handles warm-up, statistics and allocation counts. ([BenchmarkDotNet](https://benchmarkdotnet.org/))
- **`CS-PERF-02`** (SHOULD) Profile with `dotnet-trace` (CPU/events), `dotnet-counters` (live metrics), `dotnet-dump`/`dotnet-gcdump` (memory) and PerfView or a continuous profiler (Pyroscope, Datadog, Application Insights Profiler); ship `System.Diagnostics.Metrics` and OpenTelemetry for production signals. Official cross-platform diagnostic tools; no code changes. ([dotnet-trace](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-trace))
- **`CS-PERF-03`** (SHOULD) Tune the runtime deliberately: Server GC vs Workstation (`<ServerGarbageCollector>`), `<ConcurrentGarbageCollection>`, `DOTNET_GCHeapHardLimit`/container-aware limits, `TieredPGO`, ReadyToRun (`<PublishReadyToRun>`) for startup, and `ArrayPool<T>`, `ObjectPool<T>`, `Span<T>`, `stackalloc` on measured hot paths. .NET reads container cgroup limits; wrong GC mode wastes memory or throughput. ([MS: GC config](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector))
- **`CS-PERF-04`** (SHOULD) Avoid hot-path traps: string concatenation in loops (use `StringBuilder`/`string.Create`), LINQ and closures in tight loops, boxing (`object`/non-generic collections), `params object[]`, `Regex` constructed per call (use `[GeneratedRegex]`), `async` on paths that never await, logging with interpolation (use `LoggerMessage`), `DateTime.Now`, exceptions as control flow, and sync I/O. Allocations drive GC pauses. ([MS: high-performance logging](https://learn.microsoft.com/en-us/dotnet/core/extensions/high-performance-logging))
- **`CS-PERF-05`** (SHOULD) Use response caching, `OutputCache`, `HybridCache` (.NET 9+) or `IMemoryCache` with explicit expiry and size limits for repeat reads; never cache unbounded keys. Unbounded `IMemoryCache` is a leak. ([MS: output caching](https://learn.microsoft.com/en-us/aspnet/core/performance/caching/output))

## SEC: security

- **`CS-SEC-01`** (MUST) Prevent SQL injection: parameterised queries only; with EF Core use LINQ or `FromSql($"... {x}")`/`ExecuteSql` (interpolation is parameterised) and never `FromSqlRaw`/`ExecuteSqlRaw` with concatenated strings (CA2100); Dapper with anonymous parameters. Avoid `Process.Start` with user input; use `ArgumentList`. The interpolated `FromSql` is safe, `FromSqlRaw` with string concat is not. ([MS: EF Core SQL queries](https://learn.microsoft.com/en-us/ef/core/querying/sql-queries))
- **`CS-SEC-02`** (MUST) Never use `BinaryFormatter` (removed in .NET 9, throws), `NetDataContractSerializer`, `SoapFormatter`, `LosFormatter`, or Newtonsoft `TypeNameHandling` other than `None` on untrusted data; prefer `System.Text.Json` with typed models and `JsonSerializerOptions` limits; disable DTD processing in `XmlReader` (`DtdProcessing.Prohibit`, `XmlResolver = null`). Deserialization gadgets lead to RCE; XXE. ([MS: BinaryFormatter security guide](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide))
- **`CS-SEC-03`** (MUST) Web risks: validate outbound URLs (SSRF allow-list, block link-local/metadata IPs), canonicalise file paths (`Path.GetFullPath` then check the prefix; never `Path.Combine` with user input), use `LocalRedirect`/`Url.IsLocalUrl` for redirects, keep antiforgery on for cookie-authenticated endpoints (automatic for Razor/MVC form posts, explicit `AddAntiforgery`/`RequireAntiforgery` for minimal APIs), and configure CORS with named policies listing exact origins (no `AllowAnyOrigin` with credentials). OWASP A01/A10 mapping. ([MS: anti-forgery](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery))
- **`CS-SEC-04`** (MUST) Keep secrets out of source: in development use `dotnet user-secrets init` / `dotnet user-secrets set "Key" "value"` (stored under the user profile, `UserSecretsId` in the csproj; dev-only, not encrypted); in production use environment variables or Azure Key Vault via `builder.Configuration.AddAzureKeyVault(uri, new DefaultAzureCredential())` with managed identity; never commit `appsettings.Production.json` secrets. Secrets in git are permanent. ([MS: app secrets](https://learn.microsoft.com/en-us/aspnet/core/security/app-secrets))
- **`CS-SEC-05`** (MUST) Crypto: use `System.Security.Cryptography` (`AesGcm`, `RandomNumberGenerator`, `Rfc2898DeriveBytes.Pbkdf2`), ASP.NET Core Identity's `PasswordHasher` or Argon2 for passwords, `RandomNumberGenerator` (never `System.Random`) for tokens, and Data Protection API for cookies; avoid MD5/SHA1 for security, `DES`/`3DES`, ECB mode and custom crypto. Wrong primitives are not detected by tests. ([MS: cryptography model](https://learn.microsoft.com/en-us/dotnet/standard/security/cryptography-model))
- **`CS-SEC-06`** (MUST) Validate input at the adapter boundary: model binding with DataAnnotations (`[Required]`, `[StringLength]`) or FluentValidation (endpoint filter `AddEndpointFilter`), `[ApiController]` auto-400, then map to domain types that enforce invariants; never trust client-supplied ids for authorization (check ownership). Validation at the edge, invariants in the domain. ([MS: web API](https://learn.microsoft.com/en-us/aspnet/core/web-api/))
- **`CS-SEC-07`** (SHOULD) Supply chain: restore with `--locked-mode`, source mapping, signed packages (`dotnet nuget sign`, trusted signers in `nuget.config`), no `*` floating versions in applications, review new packages for typosquats, and treat MSBuild `Exec` targets/`.targets` from packages as code. NuGet has no install scripts, but analyzers and `build/` targets execute at build. ([MS: dotnet nuget sign](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-nuget-sign))
- **`CS-SEC-08`** (SHOULD) Run SAST in CI: built-in CA security rules (CA2100-CA5xxx via `AnalysisLevel`), Security Code Scan or SonarAnalyzer.CSharp, CodeQL for C#, and Semgrep `p/csharp`; set `<AnalysisMode>All</AnalysisMode>` for the Security category at least. The analyzers are free and run in the build. ([MS: code analysis overview](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/overview))
- **`CS-SEC-09`** (MUST) Enable authentication/authorization explicitly: `app.UseAuthentication(); app.UseAuthorization();`, a fallback policy that requires an authenticated user (`FallbackPolicy = RequireAuthenticatedUser`), and `[AllowAnonymous]` only where deliberate; enforce HTTPS and HSTS in production. Default-open endpoints are a common finding. ([MS: ASP.NET Core security](https://learn.microsoft.com/en-us/aspnet/core/security/))

## DATA: persistence

- **`CS-DATA-01`** (SHOULD) Use EF Core for aggregates and writes, Dapper or `FromSql`/raw ADO.NET for read-heavy reporting queries; keep the `DbContext` and entity configuration (`IEntityTypeConfiguration<T>`) in Infrastructure, and map to domain entities or use persistence-ignorant aggregates with private fields mapped by EF. One tool per access pattern; configuration objects keep Domain clean. ([MS: EF Core](https://learn.microsoft.com/en-us/ef/core/))
- **`CS-DATA-02`** (MUST) Migrations: `dotnet ef migrations add <Name> --project src/Shop.Infrastructure --startup-project src/Shop.Api`, review the generated SQL, apply in deployments with an idempotent script (`dotnet ef migrations script --idempotent`) or migration bundle (`dotnet ef migrations bundle`), never `Database.Migrate()` at app start in multi-instance production; use expand/contract for zero downtime. Concurrent instances racing migrations is a known outage cause. ([MS: applying migrations](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying))
- **`CS-DATA-03`** (MUST) Treat `DbContext` as a scoped unit of work: one `SaveChangesAsync` per use case, explicit `BeginTransactionAsync` only when spanning several saves or outbox + business write, and wrap retrying strategies (`EnableRetryOnFailure`) with `CreateExecutionStrategy().ExecuteAsync` when using user transactions. Set isolation deliberately (`ReadCommitted` default on SQL Server; use `Serializable` or optimistic concurrency tokens `[Timestamp]` for conflicts). Transaction boundaries belong in the application layer. ([MS: EF Core transactions](https://learn.microsoft.com/en-us/ef/core/saving/transactions))
- **`CS-DATA-04`** (MUST) Avoid N+1: use `Include`/`ThenInclude` or projections with `Select` to DTOs, `AsSplitQuery()` for multiple collection includes (cartesian explosion), keep lazy-loading proxies off (`UseLazyLoadingProxies` not enabled), and set `AsNoTracking()` (or `UseQueryTrackingBehavior(NoTracking)`) for read-only queries. Never call `ToListAsync()` then filter in memory. Tracking and lazy loading hide query counts. ([MS: efficient querying](https://learn.microsoft.com/en-us/ef/core/performance/efficient-querying))
- **`CS-DATA-05`** (MUST) Register the context with `AddDbContext` (scoped) or `AddDbContextPool`; never share a `DbContext` across threads or hold it in a singleton (use `IDbContextFactory<T>` in workers/Blazor); set command timeouts and use async APIs (`ToListAsync`, `SaveChangesAsync`) with the request `CancellationToken`; size the provider pool (`Maximum Pool Size`). `DbContext` is not thread-safe. ([MS: DbContext lifetime and pooling](https://learn.microsoft.com/en-us/ef/core/dbcontext-configuration/))
- **`CS-DATA-06`** (SHOULD) Use the outbox pattern for publishing events with a DB write (MassTransit/Wolverine/NServiceBus outbox) and idempotent consumers keyed by message id. A transaction cannot span DB and broker. ([MS: integration events and outbox](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/multi-container-microservice-net-applications/subscribe-events))

## API: APIs and integration

- **`CS-API-01`** (SHOULD) Choose minimal APIs (`app.MapGroup("/orders").MapPost(...)`, endpoint filters, `TypedResults`) for new services and controllers (`[ApiController]`) when MVC features (filters, model binding conventions, existing code) are needed; either way keep handlers thin and call an Application use case; lifecycle: middleware pipeline order (exception handler, HSTS, auth, authorization, rate limiter, endpoints). Both are adapters; neither belongs in Domain. ([MS: minimal APIs](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis))
- **`CS-API-02`** (SHOULD) Publish contracts with the built-in OpenAPI support (`AddOpenApi()`/`MapOpenApi()`, `Microsoft.AspNetCore.OpenApi`, .NET 9+), generate the document at build (`Microsoft.Extensions.ApiDescription.Server`) for contract diffing; version with `Asp.Versioning.Http`; use gRPC (`Grpc.AspNetCore`) for service-to-service where needed. Swashbuckle is no longer a template default since .NET 9. ([MS: OpenAPI in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/overview))
- **`CS-API-03`** (MUST) Return RFC 9457 problem details: `builder.Services.AddProblemDetails()`, `app.UseExceptionHandler()`, `app.UseStatusCodePages()`, `IExceptionHandler` implementations mapping domain errors to status codes, `Results.Problem`/`TypedResults.ValidationProblem`; never leak stack traces in production. One error shape for clients; the dev exception page is dev-only. ([MS: handle errors in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/error-handling))
- **`CS-API-04`** (MUST) Resilience with `Microsoft.Extensions.Http.Resilience` (`AddStandardResilienceHandler()` = rate limiter, total timeout, retry with exponential backoff and jitter, circuit breaker, attempt timeout; built on Polly v8) on every typed `HttpClient`; retry only idempotent calls or add idempotency keys; protect your own API with `AddRateLimiter` (fixed/sliding/token bucket/concurrency). Defaults are tuned; hand-rolled retry loops multiply load. ([MS: HTTP resilience](https://learn.microsoft.com/en-us/dotnet/core/resilience/http-resilience))
- **`CS-API-05`** (SHOULD) Messaging: use MassTransit, Wolverine or NServiceBus (or the raw Azure Service Bus / Confluent.Kafka / RabbitMQ.Client SDKs) with an outbox, at-least-once semantics, idempotent handlers, dead-letter queues and poison-message limits. Brokers deliver duplicates. ([MS: .NET microservices event bus](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/multi-container-microservice-net-applications/integration-event-based-microservice-communications))
- **`CS-API-06`** (MUST) Obtain `HttpClient` from `IHttpClientFactory` (typed or named clients via `AddHttpClient<T>()`) or a long-lived static/singleton with `SocketsHttpHandler{PooledConnectionLifetime=...}`; never `new HttpClient()` per call or inside `using` (socket exhaustion); pass the `CancellationToken` and set `Timeout`. Connection reuse and DNS refresh. ([MS: HttpClient guidelines](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/http/httpclient-guidelines))

## OBS: observability

- **`CS-OBS-01`** (MUST) Log with `ILogger<T>` and structured message templates (`logger.LogInformation("Order {OrderId} shipped", id)`, never string interpolation), compile-time `[LoggerMessage]` source generation on hot paths, scopes for correlation, and Serilog as the sink layer if needed; never log secrets or personal data. Keep `Microsoft.*` at Warning. Message templates keep fields queryable and cheap; CA2254 flags non-constant templates. ([MS: logging](https://learn.microsoft.com/en-us/dotnet/core/extensions/logging))
- **`CS-OBS-02`** (SHOULD) Emit metrics with `System.Diagnostics.Metrics` (`Meter`, `Counter<T>`, `Histogram<T>`; `IMeterFactory` from DI), names in lowercase dotted style with units, and export via OpenTelemetry (`AddOpenTelemetry().WithMetrics(...)`, OTLP, Prometheus). - **`CS-OBS-03`** (SHOULD) Trace with `System.Diagnostics.ActivitySource`/`Activity` and OpenTelemetry .NET (tracing and metrics stable; logs stable since 1.x), auto-instrument ASP.NET Core, `HttpClient`, EF Core/SqlClient; W3C `traceparent` propagates automatically; add `trace_id` to log scopes. Cross-service correlation. ([MS: observability with OTel](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/observability-with-otel))
- **`CS-OBS-04`** (MUST) Expose health endpoints: `AddHealthChecks()` with `MapHealthChecks("/healthz/live", predicate: _ => false)` for liveness (no dependencies) and `/healthz/ready` with tagged dependency checks for readiness; do not expose detailed responses publicly. Orchestrators restart on liveness; readiness gates traffic. ([MS: health checks](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/health-checks))
- **`CS-OBS-05`** (SHOULD) Include an `ILogger` correlation id (`Activity.Current?.TraceId`) in problem details; redact sensitive fields with `Microsoft.Extensions.Compliance.Redaction` or `[LogProperties]`. Support can find a request from a client error. ([MS: data redaction](https://learn.microsoft.com/en-us/dotnet/core/extensions/data-redaction))

## OPS: configuration, packaging and deployment

- **`CS-OPS-01`** (MUST) Bind typed options: `builder.Services.AddOptions<SmtpOptions>().BindConfiguration("Smtp").ValidateDataAnnotations().ValidateOnStart()`; inject `IOptions<T>` (singleton), `IOptionsSnapshot<T>` (scoped) or `IOptionsMonitor<T>`; layering is `appsettings.json` < `appsettings.{Environment}.json` < user-secrets < environment variables (`Section__Key`) < command line. Fail at startup on bad config (12-factor). ([MS: configuration](https://learn.microsoft.com/en-us/dotnet/core/extensions/configuration))
- **`CS-OPS-02`** (SHOULD) Package as a container: `dotnet publish -c Release` with the built-in container support (`dotnet publish -t:PublishContainer`, `ContainerBaseImage`), or a multi-stage Dockerfile (`mcr.microsoft.com/dotnet/sdk:10.0` build, `mcr.microsoft.com/dotnet/aspnet:10.0` runtime or `-noble-chiseled`/`-alpine`), non-root user (images run as `app` UID 1654 from .NET 8), `restore` layer before `COPY . .`. Small, non-root, cache-friendly images. ([MS: containerize with SDK](https://learn.microsoft.com/en-us/dotnet/core/docker/publish-as-container))
- **`CS-OPS-03`** (SHOULD) Use NativeAOT (`<PublishAot>true</PublishAot>`, `dotnet publish -r linux-x64`) only for small services, Lambda/functions and CLIs that are trim-safe: no runtime reflection/`dynamic`/`Assembly.Load`, `System.Text.Json` source generation, minimal APIs via `CreateSlimBuilder`/`WebApplication.CreateSlimBuilder`; EF Core and MVC are not AOT-ready. Resolve IL2026/IL3050 warnings as errors. Otherwise use ReadyToRun + trimming carefully. Fast start and low memory, at the cost of a restricted feature set. ([MS: Native AOT deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/))
- **`CS-OPS-04`** (MUST) Handle shutdown via the generic host: `IHostApplicationLifetime`, `SIGTERM` is handled automatically (`ConsoleLifetime`), set `HostOptions.ShutdownTimeout` (default 30 s from .NET 8) below the orchestrator's grace period, stop accepting traffic (readiness false) then drain in-flight requests. Prevents dropped requests on deploy. ([MS: generic host shutdown](https://learn.microsoft.com/en-us/dotnet/core/extensions/generic-host))
- **`CS-OPS-05`** (MUST) Scope only build output and tmp per run: `DOTNET_CLI_HOME` (first-run state, tool cache) and `TMPDIR`. Keep the download caches shared (`NUGET_PACKAGES`, `NUGET_HTTP_CACHE_PATH`, `NUGET_PLUGINS_CACHE_PATH`; NuGet locks them), since a per-run copy re-downloads every package (TOOLING D15). Set `MSBUILDDISABLENODEREUSE=1`, `DOTNET_NOLOGO=1` (replaces the unsupported `DOTNET_SKIP_FIRST_TIME_EXPERIENCE`) and `DOTNET_CLI_TELEMETRY_OPTOUT=1` as pack env, and end a run with `dotnet build-server shutdown` so no MSBuild/Roslyn/Razor server outlives it. Node reuse leaves resident processes that hold files in the run directory. ([MS: manage global packages and cache folders](https://learn.microsoft.com/en-us/nuget/consume-packages/managing-the-global-packages-and-cache-folders))
- **`CS-OPS-06`** (MUST) Treat as build artifacts to clean: `bin/`, `obj/`, `TestResults/`, `**/coverage.cobertura.xml`, `*.coverage`, `*.trx`, `*.binlog`, `BenchmarkDotNet.Artifacts/`, `.vs/`, `publish/`, `artifacts/` (with `<UseArtifactsOutput>`), `*.nupkg`/`*.snupkg`, `mono_crash.*.json`, and core dumps; `dotnet clean` does not remove `obj` restore state or `TestResults`. Drives the loops cleanup and `.gitignore` (`dotnet new gitignore`). ([MS: artifacts output layout](https://learn.microsoft.com/en-us/dotnet/core/sdk/artifacts-output))
- **`CS-OPS-07`** (SHOULD) Prefer the SDK's `Directory.Build.props` `<UseArtifactsOutput>true</UseArtifactsOutput>` (`artifacts/bin`, `artifacts/obj`, `artifacts/publish`) in new repos so a single directory holds all outputs. One folder to ignore and clean. ([MS: artifacts output layout](https://learn.microsoft.com/en-us/dotnet/core/sdk/artifacts-output))

## DOC: documentation and review

- **`CS-DOC-01`** (SHOULD) Document public API with XML doc comments (`<summary>`, `<param>`, `<returns>`, `<exception>`), set `<GenerateDocumentationFile>true</GenerateDocumentationFile>` (CS1591 on missing docs for libraries), and publish with DocFX; services can rely on OpenAPI plus summaries (`WithSummary`, `WithDescription`). XML docs feed IntelliSense and DocFX. ([MS: XML documentation comments](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/xmldoc/))
- **`CS-DOC-02`** (SHOULD) Keep a README (build, test, run, config keys, migrations), `docs/adr/NNNN-*.md` for decisions, `CHANGELOG.md` or GitHub release notes, and a `CONTRIBUTING.md` that names the exact `dotnet` commands. New contributors can reproduce the gate locally. ([MS: .NET docs contributor guide](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute))
- **`CS-DOC-03`** (SHOULD) Reviewers look first for: sync-over-async and missing `CancellationToken`; `DbContext` lifetime and N+1; nullable warnings suppressed with `!`; `HttpClient` creation; exceptions swallowed; secrets in config; public API surface growth; missing tests for new branches. Highest-yield defects in ASP.NET Core code reviews. ([MS: ASP.NET Core best practices](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/best-practices))
- **`CS-DOC-04`** (SHOULD) Track API compatibility of libraries with `<EnablePackageValidation>true</EnablePackageValidation>` and `<PackageValidationBaselineVersion>` so a pack fails on breaking changes; document breaking changes in the changelog. SemVer needs a check. ([MS: package validation](https://learn.microsoft.com/en-us/dotnet/fundamentals/apicompat/package-validation/overview))

## FW: frameworks

- **`CS-FW-01`** (SHOULD) Dominant backend frameworks: ASP.NET Core (Web API, minimal APIs, MVC, Razor Pages, SignalR, gRPC), EF Core (ORM, with Dapper beside it), the generic host/Worker Service, and .NET Aspire for local orchestration and telemetry; Azure Functions for serverless. Usage evidence: the Stack Overflow Developer Survey lists ASP.NET Core and .NET as top web frameworks every year. Pack content targets these. ([ASP.NET Core](https://github.com/dotnet/aspnetcore))
- **`CS-FW-02`** (SHOULD) Follow the framework where the project uses it: ASP.NET Core's `Program.cs` is the composition root, `appsettings` is configuration, `WebApplicationFactory` is the integration harness, EF Core's `DbContext` already implements unit of work and repository, and the default folder templates (`Controllers/`, `Models/`) conflict with hexagonal; keep them only inside the inbound adapter project. Project rules win; log overrides. Fighting the framework costs more than it returns. ([MS: ASP.NET Core architecture](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures))
- **`CS-FW-03`** (AVOID) Framework footguns: scoped service injected into a singleton (captive dependency, caught by `ValidateScopes`); `DbContext` shared across threads; middleware order wrong (auth before routing issues); `IOptions` values read at startup but expected to reload; synchronous `Stream` reads in Kestrel (disallowed by default); minimal API parameter binding ambiguity; MediatR licence change (v13+ dual RPL-1.5/commercial) and Moq/FluentAssertions licence/telemetry changes affecting CI. Each has bitten production teams. ([MS: DI guidelines](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/guidelines))
- **`CS-FW-04`** (SHOULD) Pick the host model deliberately: `WebApplication.CreateBuilder` for HTTP, `Host.CreateApplicationBuilder` for workers, `CreateSlimBuilder` for AOT; share cross-host composition in a `ServiceDefaults` project (Aspire pattern) for telemetry, health, resilience. One consistent baseline across services. ([MS: generic host](https://learn.microsoft.com/en-us/dotnet/core/extensions/generic-host))

## Top 10 footguns

1. Sync-over-async: `service.GetAsync().Result` -> `await service.GetAsync(ct)` all the way up (CS-CONC-05).
2. `async void` -> return `Task`; exceptions in `async void` crash the process (CS-CONC-05).
3. `new HttpClient()` per call -> `IHttpClientFactory` or a long-lived client (CS-API-06).
4. EF Core N+1 and tracked read-only queries -> `Include`/projection, `AsNoTracking()`, `AsSplitQuery()` (CS-DATA-04).
5. `DbContext` held by a singleton or shared across `Task.WhenAll` -> scoped lifetime or `IDbContextFactory<T>` (CS-DATA-05).
6. Captive dependencies (singleton holding a scoped service) -> `ValidateScopes`/`ValidateOnBuild`, `IServiceScopeFactory` (CS-ARCH-05, CS-FW-03).
7. Null-forgiving `!` and ignored nullable warnings -> honest annotations, `required`, guard clauses, warnings as errors (CS-IDIOM-03, CS-TOOL-05).
8. `throw ex;` and swallowed exceptions -> `throw;`, catch specific types (CS-IDIOM-01).
9. `DateTime.Now` and culture-sensitive string ops -> `TimeProvider.GetUtcNow()`, `StringComparison.Ordinal` (CS-ARCH-07, CS-IDIOM-07).
10. `FromSqlRaw` with concatenation, `BinaryFormatter`, `TypeNameHandling.All` -> parameterised `FromSql`, `System.Text.Json` (CS-SEC-01, CS-SEC-02).
