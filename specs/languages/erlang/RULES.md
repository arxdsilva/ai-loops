# Erlang (OTP, rebar3) rules

Erlang/OTP 29.1 (OTP 28 and 27 still patched), rebar3 3.28, as of 2026-11. Source: `research/languages/erlang.md` (rule IDs kept; Verification applied). Pack: `specs/languages/erlang/pack.json`. Universal rules are not repeated: layering is `specs/ARCHITECTURE.md`, SOLID is `specs/SOLID.md`.

Project rules win: follow the project's own config (`rebar.config`, `elvis.config`, `.editorconfig`, framework conventions) over these defaults, and log every override with `loops run override`.

Race policy: the BEAM shares nothing between processes, so `race.mode = none`. The gate enforces the substitute: `eunit` and `ct` run once per `race.variants` entry (`ERL_FLAGS="+S 1:1"`, then `"+S 8:8"`), see `ERL-CONC-04`. Concuerror is dropped (D21): its last Hex release is 2020.


Arch: the pack has no import parser (`module:function(` matches atoms and maps); direction is enforced by `rebar3 xref` (the `xref` arch check) and the `.app.src` `applications` list (`ERL-ARCH-01/02`).

## REPO

- **`ERL-REPO-01`** (MUST) Create projects with `rebar3 new app`, `lib`, `release` or `umbrella` and keep the standard OTP app layout: `src/`, `include/`, `priv/`, `test/`, and `<app>.app.src` in `src/`. Why: rebar3, Common Test and relx find code only by this layout. ([rebar3 getting started](https://rebar3.org/docs/getting-started/)) ([OTP applications](https://www.erlang.org/doc/system/applications.html))
- **`ERL-REPO-02`** (SHOULD) Use `apps/` (umbrella) when the service has several OTP apps; use `lib/` only for libraries you ship together. Keep one release per deployable. Why: One app per layer makes app dependencies the architecture boundary. ([Adopting Erlang: development](https://adoptingerlang.org/docs/development/)) ([rebar3 releases](https://rebar3.org/docs/deployment/releases/))
- **`ERL-REPO-03`** (SHOULD) Split a repo only at a deployable or release boundary; otherwise keep a rebar3 umbrella. Do not use Bazel or Nx for Erlang unless the org already runs it. Why: rebar3 handles multi-app natively; extra build systems fight `_build`. ([Adopting Erlang](https://adoptingerlang.org/)) ([Erlang.mk guide](https://erlang.mk/guide/))
- **`ERL-REPO-04`** (MUST) Commit `rebar.lock` for applications and releases; for a Hex library commit it too (it is not published) but declare ranges in `rebar.config`. Why: The lock holds immutable git refs, versions and package hashes against hijacked mirrors. ([rebar3 dependencies](https://rebar3.org/docs/configuration/dependencies/))
- **`ERL-REPO-05`** (MUST) Declare deps with `"~> X.Y"` ranges for Hex packages, `{tag, ...}` or `{ref, ...}` (never `{branch, ...}`) for git deps. Use `{deps_error_on_conflict, true}`. Why: Branch deps make `rebar.lock` the only reproducibility; conflicts are otherwise skipped silently (level-order, shallowest wins). ([rebar3 dependencies](https://rebar3.org/docs/configuration/dependencies/))
- **`ERL-REPO-06`** (SHOULD) Use `rebar3 upgrade <dep>` to bump one dep and `rebar3 tree` to inspect; never hand-edit `rebar.lock`. Remove unused deps with `rebar3_hank` or `rebar3 xref`. Why: Keeps the transitive tree minimal and auditable. ([rebar3 commands](https://rebar3.org/docs/commands/)) ([rebar3_hank](https://github.com/AdRoll/rebar3_hank))
- **`ERL-REPO-07`** (SHOULD) Neither Renovate nor Dependabot supports rebar3 natively (Renovate has no rebar manager; Dependabot's Hex support is `mix` only), so schedule a CI job that runs `rebar3 upgrade` and opens a PR, or add a Renovate regex manager for `rebar.config`. Why: Lockfile drift and old OTP-bound deps are the main supply-chain risk. ([Renovate docs](https://docs.renovatebot.com/modules/manager/))
- **`ERL-REPO-08`** (SHOULD) Publish libraries to Hex with `rebar3 hex publish` (plugin `rebar3_hex`), SemVer, a `CHANGELOG.md`, `{licenses,...}` and `{links,...}` in `.app.src`; use Hex package scopes or a private repo for internal packages. Why: Hex is the registry; metadata lives in `.app.src`. ([Hex publish](https://hex.pm/docs/publish)) ([rebar3_hex](https://hexdocs.pm/rebar3_hex/))
- **`ERL-REPO-09`** (MUST) Pin the toolchain with `.tool-versions` (asdf or mise: `erlang`, `rebar`) and `{minimum_otp_vsn, "27"}` in `rebar.config`. Build CI from the same pin. Why: OTP major drives compiler warnings, Dialyzer and JIT behaviour. ([rebar3 config](https://rebar3.org/docs/configuration/configuration/))
- **`ERL-REPO-10`** (MUST) `.gitignore`: `_build/`, `*.beam`, `erl_crash.dump`, `rebar3.crashdump`, `ct_logs/`, `*.coverdata`, `.rebar3/`, `*.plt`, `bom.xml`, `Mnesia.*/`, `cover/`, `*.tar.gz`. Add `.editorconfig` (4-space indent, no tabs). Commit `rebar.lock`, `elvis.config`. Why: These files are artifacts; committing them poisons diffs and caches. ([rebar3 basic usage](https://rebar3.org/docs/basic_usage/)) ([OTP crash dump](https://www.erlang.org/doc/apps/erts/crash_dump.html))
- **`ERL-REPO-11`** (SHOULD) CI order: restore `_build` and `~/.cache/rebar3` cache keyed on `rebar.lock` + OTP version, then `rebar3 compile`, `fmt --check`, `lint`, `xref`, `dialyzer`, `eunit`, `ct`, `proper`, `cover`, `sbom`. Matrix: the OTP majors still patched (28, 29; 27 until dropped). Why: Cheapest gates first; PLT and deps are the slow parts. ([rebar3 commands](https://rebar3.org/docs/commands/)) ([OTP SECURITY.md](https://github.com/erlang/otp/blob/master/SECURITY.md))
- **`ERL-REPO-12`** (SHOULD) Use conventional commits; generate changelogs from them or keep `CHANGELOG.md`. Why: the commit level then drives the version and the changelog. ([Conventional Commits](https://www.conventionalcommits.org/))

## TOOL

- **`ERL-TOOL-01`** (MUST) Target OTP 28 or 29. OTP 29.0 shipped 2026-05-13 (29.1.2 current), OTP 28 latest patch 28.5.0.8, OTP 27 27.3.4.19; OTP has no LTS and patches only the last 3 majors; one major is released each year (May). Install with asdf or mise. Why: Running an unpatched major leaves known CVEs. ([OTP downloads](https://www.erlang.org/downloads)) ([OTP SECURITY.md](https://github.com/erlang/otp/blob/master/SECURITY.md))
- **`ERL-TOOL-02`** (MUST) Format with erlfmt: add `{project_plugins, [erlfmt]}.` and `{erlfmt, [write]}`; CI runs `rebar3 fmt --check`. Opt a file out only with `%%% % @noformat` or a form with `%% erlfmt:ignore <reason>`. Why: One formatter ends style debate; erlfmt is feature-complete (1.0). ([erlfmt](https://github.com/WhatsApp/erlfmt))
- **`ERL-TOOL-03`** (MUST) Compile with `{erl_opts, [debug_info, warnings_as_errors, warn_export_vars, warn_unused_import, warn_missing_spec]}`. Never ship with `nowarn_*` blanket options. Why: The compiler catches unused vars, bad guards, deprecated calls (OTP 29 warns on `-unsafe` functions). ([rebar3 config](https://rebar3.org/docs/configuration/configuration/)) ([OTP 29.0](https://www.erlang.org/patches/OTP-29.0))
- **`ERL-TOOL-04`** (MUST) Run `rebar3 xref` with `{xref_checks, [undefined_function_calls, undefined_functions, locals_not_used, deprecated_function_calls, deprecated_functions]}`. Why: Finds calls to missing modules and dead exports, and checks the app-level dependency direction. ([rebar3 config](https://rebar3.org/docs/configuration/configuration/)) ([Xref](https://www.erlang.org/doc/apps/tools/xref_chapter.html))
- **`ERL-TOOL-05`** (SHOULD) Lint with Elvis through `rebar3_lint`: `rebar3 lint`; rulesets `erl_files`, `hrl_files`, `rebar_config`, `gitignore`; `warnings_as_errors` defaults to true so findings exit non-zero. Keep `elvis.config` in git and run the check only when it exists: `rebar3 lint` exits 1 with no `elvis.config` or `{elvis, ...}` entry (rebar3_lint 6.0.0). Why: Enforces nesting depth, naming, line length, no `try ... catch _:_` swallow. ([elvis_core](https://github.com/inaka/elvis_core)) ([rebar3_lint](https://github.com/inaka/rebar3_lint))
- **`ERL-TOOL-06`** (MUST) Type-check with Dialyzer: `rebar3 dialyzer` (use `--incremental` locally) with `{dialyzer, [{warnings, [unmatched_returns, error_handling, underspecs]}, {plt_extra_apps, [...]}]}`. Why: Success typing finds dead code and contract breaks; first run builds a PLT, cache it. ([Dialyzer](https://www.erlang.org/doc/apps/dialyzer/dialyzer.html)) ([rebar3 commands](https://rebar3.org/docs/commands/))
- **`ERL-TOOL-07`** (SHOULD) For gradual stricter typing use eqWAlizer through ELP: add `eqwalizer_support` dep, run `elp eqwalize-all`. It needs OTP 26+; the standalone repo is archived and development is in ELP. Treat it as optional on top of Dialyzer, never as a required gate. Why: eqWAlizer is stricter (sound) but has a different checking model and costs annotation effort. ([eqWAlizer](https://github.com/WhatsApp/eqwalizer)) ([ELP](https://whatsapp.github.io/erlang-language-platform/))
- **`ERL-TOOL-08`** (SHOULD) Audit dependencies: `rebar3_audit` plugin (`rebar3 audit`, v0.2.8, 2026-09; it queries the GitHub Advisory Database, so it needs network access to api.github.com, optionally `GITHUB_TOKEN` for rate limits; single maintainer, and its Hex-linked repo URL is dead) and CycloneDX SBOM with `rebar3 sbom` (writes `./bom.xml`, `-F json` for `bom.json`). Pin rebar3 >= 3.27.0 (CVE-2026-21619 fixes). Check OSV-Scanner support for `rebar.lock` before relying on it. Why: Hex advisories and rebar3 CVEs exist; scanner support for `rebar.lock` is young. ([rebar3_audit](https://hex.pm/packages/rebar3_audit)) ([rebar3_sbom](https://github.com/erlef/rebar3_sbom))
- **`ERL-TOOL-09`** (SHOULD) Editor baseline: ELP (Erlang Language Platform) as LSP; turn off any second formatter on save so erlfmt wins. Why: Two formatters fight. ([ELP](https://whatsapp.github.io/erlang-language-platform/)) ([erlfmt](https://github.com/WhatsApp/erlfmt))

## ARCH

- **`ERL-ARCH-01`** (MUST) Make each hexagon layer its own OTP application; list only inward dependencies in `.app.src` `applications`. Domain lists `[kernel, stdlib]` only. Why: The `applications` list is the start order and the declared boundary. ([OTP applications](https://www.erlang.org/doc/system/applications.html))
- **`ERL-ARCH-02`** (MUST) Modules are flat atoms: `module:function(...)` names the module only, so enforce app boundaries with xref queries or an import scan, with a per-app module prefix (`ms_pg_*`). The module name must equal the file name. Why: There is no `internal/` or visibility between apps; any exported function can be called. ([Erlang reference: modules](https://www.erlang.org/doc/system/reference_manual.html)) ([Xref](https://www.erlang.org/doc/apps/tools/xref_chapter.html))
- **`ERL-ARCH-03`** (SHOULD) Keep the exported API of each app small: `-export` only the facade; mark internals with `-doc false.` (OTP 27+) and `-export_type` only public types. Why: Exports are the only visibility control; hidden docs signal internals. ([Erlang reference: modules](https://www.erlang.org/doc/system/reference_manual.html)) ([documentation](https://www.erlang.org/doc/system/documentation.html))
- **`ERL-ARCH-04`** (MUST) Import cycles between apps are legal for the compiler but forbidden here: run xref and an app-graph check (`rebar3 tree`, `.app.src` `applications`). Why: Cycles break release start order and hot upgrades. ([OTP applications](https://www.erlang.org/doc/system/applications.html)) ([rebar3 commands](https://rebar3.org/docs/commands/))
- **`ERL-ARCH-05`** (MUST) Define ports as `-callback` behaviours in the consuming app (`ms_app_repo`), implement in the adapter app, and inject the implementation module through app env or a function argument at the composition root. Why: Behaviours are the idiomatic port; consumer owns the interface. ([OTP design principles](https://www.erlang.org/doc/system/design_principles.html))
- **`ERL-ARCH-06`** (MUST) The composition root is the release app: `start/2` builds the supervision tree and wires adapters via `application:set_env`. No `application:get_env` calls inside the domain. Why: Config at the edge keeps the domain pure; avoids a service locator. ([OTP applications](https://www.erlang.org/doc/system/applications.html)) ([rebar3 releases](https://rebar3.org/docs/deployment/releases/))
- **`ERL-ARCH-07`** (MUST) Domain apps contain no processes, no `ets`, `file`, `gen_tcp`, `httpc`, `os:`, `erlang:now/system_time`, `os:timestamp`, `rand:` or `!`. Pass time and random values in as arguments. Why: Pure functions are trivial to property-test and cannot race. ([Erlang efficiency/process guide](https://www.erlang.org/doc/system/eff_guide_processes.html))
- **`ERL-ARCH-08`** (AVOID) Put a process around state only when state must be serialised or has its own lifecycle; do not make a gen_server per use case or "service" just for code organisation. Why: Processes serialise calls and add a bottleneck and mailbox; modules and functions are free. ([OTP design principles](https://www.erlang.org/doc/system/design_principles.html)) ([Adopting Erlang](https://adoptingerlang.org/docs/development/))
- **`ERL-ARCH-09`** (MUST) Use `gen_statem` (callback mode `state_functions` or `handle_event_function`) for state machines and sagas; use `gen_server` for stateful servers; `gen_event` only for pluggable handlers; every long-lived process under a supervisor. Why: Gen behaviours give sys/trace, code upgrade and supervision for free. ([gen_statem](https://www.erlang.org/doc/apps/stdlib/gen_statem.html)) ([gen_event](https://www.erlang.org/doc/apps/stdlib/gen_event.html))
- **`ERL-ARCH-10`** (MUST) Choose supervisor strategy deliberately: `one_for_one` default, `rest_for_one` for ordered dependencies, `one_for_all` for tightly coupled siblings, `simple_one_for_one` replaced by dynamic `one_for_one` with `child_spec`; set `intensity` and `period`; use `significant` and `auto_shutdown` where needed. Why: Restart intensity decides when a crash escalates. ([Supervisor principles](https://www.erlang.org/doc/system/sup_princ.html)) ([supervisor](https://www.erlang.org/doc/apps/stdlib/supervisor.html))
- **`ERL-ARCH-11`** (SHOULD) SOLID size heuristics for Erlang: modules under about 400 lines, functions under about 25 lines and 5 parameters; split large `handle_call` clauses into helper functions. Why: Erlang function-clause style bloats quickly. ([Inaka Erlang guidelines](https://github.com/inaka/erlang_guidelines))

## IDIOM

- **`ERL-IDIOM-01`** (MUST) "Let it crash": return `{ok, V}` / `{error, Reason}` for expected outcomes, and crash (match failure, `error/1`) on programmer errors and corrupt state; never catch to hide. Do not write defensive code for unspecified inputs. Why: Supervisors restore a clean state; defensive code hides bugs. ([Robustness (OTP)](https://www.erlang.org/doc/system/robustness.html)) ([LYSE errors and processes](https://learnyousomeerlang.com/errors-and-processes))
- **`ERL-IDIOM-02`** (AVOID) Avoid `catch Expr` and `try ... catch _:_ -> ok`; catch a specific `Class:Reason:Stacktrace` and re-raise with `erlang:raise/3`. Why: Bare catches swallow `exit` and `throw` and lose stack traces. ([Inaka guidelines](https://github.com/inaka/erlang_guidelines)) ([Elvis rules](https://github.com/inaka/elvis_core))
- **`ERL-IDIOM-03`** (MUST) Use `try ... after` for cleanup and `monitor` or links for process cleanup; never leave open sockets, ports or files without an owner process. Why: Resources are tied to the owning process; the VM closes ports when it dies. ([Erlang reference: expressions](https://www.erlang.org/doc/system/expressions.html)) ([Robustness](https://www.erlang.org/doc/system/robustness.html))
- **`ERL-IDIOM-04`** (SHOULD) Absence is an explicit value: `undefined`, `error`, `{ok, V}`, `none`; use `maps:find/2` and `maps:get/3` with defaults, not `maps:get/2` unless a crash is wanted. Why: There is no null; `undefined` leaks silently. ([maps](https://www.erlang.org/doc/apps/stdlib/maps.html))
- **`ERL-IDIOM-05`** (SHOULD) Data is immutable: model entities as records or maps with `-type` specs; keep a record definition in one `.hrl` per app and never share it across apps (share through an accessor or a map). Why: A shared record couples apps at compile time and breaks hot upgrade. ([Erlang reference: records](https://www.erlang.org/doc/system/ref_man_records.html)) ([typespec](https://www.erlang.org/doc/system/typespec.html))
- **`ERL-IDIOM-06`** (MUST) Write a `-spec` for every exported function and `-type` for every exported data shape; add `-opaque` for value objects whose internals must stay hidden. Why: Specs feed Dialyzer, docs and ELP. ([Types and function specifications](https://www.erlang.org/doc/system/typespec.html))
- **`ERL-IDIOM-07`** (SHOULD) Use pattern matching in function heads and guards; use strict generators (`<:-`, OTP 28) in comprehensions so a non-matching element crashes instead of being skipped. Note old-style guard tests are scheduled for removal in OTP 30. Why: Silent filtering in comprehensions hides data bugs. ([OTP 28 highlights](https://www.erlang.org/blog/highlights-otp-28/)) ([OTP 29.0](https://www.erlang.org/patches/OTP-29.0))
- **`ERL-IDIOM-08`** (SHOULD) Strings are binaries (`<<"x"/utf8>>`) in the service layer; lists of integers only for legacy APIs. Use the `string` module (Unicode-aware, not `lists:` functions) and `uri_string`. Build output as iolists. Why: Binary matching is fast, memory is small; charlists break Unicode and 8-byte-per-char cost. ([Efficiency guide](https://www.erlang.org/doc/system/efficiency_guide.html)) ([uri_string](https://www.erlang.org/doc/apps/stdlib/uri_string.html))
- **`ERL-IDIOM-09`** (SHOULD) Time: use `erlang:system_time/1` / `erlang:monotonic_time/1` and `calendar` with UTC (`calendar:universal_time()`); avoid `now/0`, `erlang:now/0` and `os:timestamp` in domain code; inject a clock. Why: Time warps and testability. ([calendar](https://www.erlang.org/doc/apps/stdlib/calendar.html))
- **`ERL-IDIOM-10`** (SHOULD) Naming: `snake_case` for modules, functions, atoms, variables `CamelCase`; module prefix per app; `-spec` after the doc; max 100 columns; `-moduledoc`/`-doc` on public modules. Why: OTP and Inaka conventions; erlfmt enforces layout. ([Inaka guidelines](https://github.com/inaka/erlang_guidelines)) ([OTP documentation](https://www.erlang.org/doc/system/documentation.html))
- **`ERL-IDIOM-11`** (AVOID) Macros and parse transforms: use macros only for constants, logging and `?assert*`; avoid parse transforms (hide code from Dialyzer, xref and ELP) and avoid `-compile(export_all)` and `-compile(nowarn_export_all)`. Why: Metaprogramming defeats the static tools. ([Inaka guidelines](https://github.com/inaka/erlang_guidelines)) ([Erlang reference: macros](https://www.erlang.org/doc/system/reference_manual.html))
- **`ERL-IDIOM-12`** (MUST) Footgun: never create atoms from external input (`list_to_atom`, `binary_to_atom`, `erlang:binary_to_term/1`). Use `binary_to_existing_atom/2` or a lookup table. Why: The atom table is finite (default 1,048,576) and never garbage-collected: a crash of the whole VM. ([EEF atoms](https://security.erlef.org/secure_coding_and_deployment_hardening/serialisation)) ([erlang module](https://www.erlang.org/doc/apps/erts/erlang.html))
- **`ERL-IDIOM-13`** (SHOULD) Footgun: `++` and `lists:append` in loops on the left-hand side are O(n); build lists with cons and `lists:reverse/1`; use `maps` for lookup, not `proplists`/`lists:keyfind` over large lists. Why: Quadratic behaviour in hot paths. ([Efficiency guide: functions](https://www.erlang.org/doc/system/eff_guide_functions.html))

## CONC

- **`ERL-CONC-01`** (MUST) Model: lightweight processes, preemptive schedulers (one per core), asynchronous message passing with copy semantics; large binaries (>64 bytes) are reference counted off-heap. Spawn per independent unit of work, not per request step. Why: Isolation is the data-race defence. ([Processes (reference manual)](https://www.erlang.org/doc/system/ref_man_processes.html)) ([Efficiency guide: processes](https://www.erlang.org/doc/system/eff_guide_processes.html))
- **`ERL-CONC-02`** (MUST) Share state by messages. Where shared mutable state is needed use ETS with `{write_concurrency, true}`, `{read_concurrency, true}` and a single owner process; use `persistent_term` only for read-mostly data (updates trigger a global GC scan). Why: Races remain at ETS read-modify-write and message-ordering level. ([ets](https://www.erlang.org/doc/apps/stdlib/ets.html)) ([persistent_term](https://www.erlang.org/doc/apps/erts/persistent_term.html))
- **`ERL-CONC-03`** (SHOULD) There is no race detector. Hunt races with PropEr stateful tests (`proper_statem:parallel_commands/1`) and repeat or re-schedule runs (`rebar3 ct --repeat N`). Do not add Concuerror: its last Hex release is 2020 (README: OTP 20.3 to 23.3) and the pack drops it (D21). Why: no sanitizer exists; be honest about the gap. ([PropEr](https://github.com/proper-testing/proper)) ([rebar3_proper](https://github.com/ferd/rebar3_proper))
- **`ERL-CONC-04`** (MUST) `loops gate` runs `eunit` and `ct` once per `race.variants` entry: `ERL_FLAGS="+S 1:1"` and `ERL_FLAGS="+S 8:8"`. A failure in either blocks; a test that passes under only one setting is flaky. Why: a cheap proxy for timing-dependent races (a defect-sampling substitute, not a proof). ([erl +S](https://www.erlang.org/doc/apps/erts/erl_cmd.html)) ([rebar3 commands](https://rebar3.org/docs/commands/))
- **`ERL-CONC-05`** (MUST) Never rely on message order across different senders; only the pairwise order between two processes is guaranteed. Use `gen_server:call` correlation, monitors and references (`make_ref`/`alias`), not sleeps. OTP 28 priority messages are opt-in; do not use them to fix ordering bugs. Why: Ordering assumptions are the main logic race in Erlang. ([Processes: signals](https://www.erlang.org/doc/system/ref_man_processes.html)) ([OTP 28 highlights](https://www.erlang.org/blog/highlights-otp-28/))
- **`ERL-CONC-06`** (MUST) Async pitfalls: every `gen_server:call` has a timeout (default 5000 ms, choose it); never call yourself; avoid `gen_server:call` cycles; do not do blocking IO in a gen_server that serves many callers: hand off to a worker or use `gen_server:reply/2`. Why: Calls block; a stuck callback blocks all clients. ([gen_server](https://www.erlang.org/doc/apps/stdlib/gen_server.html)) ([Adopting Erlang](https://adoptingerlang.org/docs/development/))
- **`ERL-CONC-07`** (MUST) Mailbox overload: bound queues (admission control, a pool such as `poolboy`/`pooler`, or a `max_heap_size` and `message_queue_data` flag on the process); selective `receive` over a large mailbox is O(n), avoid it; use `process_info(Pid, message_queue_len)` as a health metric. Why: An unbounded mailbox grows until the VM dies, and burst load has no natural backpressure. ([erlang module](https://www.erlang.org/doc/apps/erts/erlang.html)) ([Efficiency guide: processes](https://www.erlang.org/doc/system/eff_guide_processes.html))
- **`ERL-CONC-08`** (MUST) Background work: use supervised workers, `proc_lib`/`gen_*` (not bare `spawn`), `erpc` for remote calls with timeout, and a graceful stop via `application:stop` and `init:stop()` with supervisor `shutdown` times. Why: Bare `spawn` is invisible to supervisors and crash reports. ([proc_lib](https://www.erlang.org/doc/apps/stdlib/proc_lib.html)) ([erpc](https://www.erlang.org/doc/apps/kernel/erpc.html))
- **`ERL-CONC-09`** (SHOULD) Distribution use: keep to horizontal clusters; do not couple application and DB tiers over Erlang distribution; use `pg` for groups. Why: Distribution removes isolation between nodes. ([EEF distribution](https://security.erlef.org/secure_coding_and_deployment_hardening/distribution))

## TEST

- **`ERL-TEST-01`** (MUST) Use EUnit for unit tests (`*_tests.erl` next to or under `test/`), Common Test for integration and system tests (`*_SUITE.erl`), PropEr for properties. Run with `rebar3 eunit`, `rebar3 ct`, `rebar3 proper`. Why: EUnit is light; CT has suites, groups, config, hooks, logs. ([EUnit](https://www.erlang.org/doc/apps/eunit/chapter.html)) ([Common Test](https://www.erlang.org/doc/apps/common_test/introduction.html))
- **`ERL-TEST-02`** (MUST) Test file globs: `**/test/*_SUITE.erl`, `**/test/*_tests.erl`, `**/src/*_tests.erl`, `**/test/prop_*.erl`, `**/test/*_SUITE_data/**`; `rebar3 ct` compiles every `*_SUITE.erl` in `test/` but not recursively. Why: loops must tell test files from code. ([rebar3 ct](https://rebar3.org/docs/testing/ct/))
- **`ERL-TEST-03`** (SHOULD) Style: one CT suite per use case with `all/0`, `groups/0`, `init_per_suite`/`end_per_suite`, `init_per_testcase`; test names `<function>_<condition>_<result>`; EUnit uses generators and fixtures (`{setup, ...}`, `{foreach, ...}`) rather than copy-paste. Why: Fixtures give setup, teardown and parallel groups. ([Common Test](https://www.erlang.org/doc/apps/common_test/introduction.html)) ([EUnit](https://www.erlang.org/doc/apps/eunit/chapter.html))
- **`ERL-TEST-04`** (SHOULD) Prefer fakes (an ETS-backed or in-memory implementation of the port behaviour) over mocks; use `meck` only for third-party modules you cannot wrap, and `meck:unload` in teardown. Why: Mocking global modules is process-global and breaks parallel tests. ([meck](https://hex.pm/packages/meck)) ([OTP design principles](https://www.erlang.org/doc/system/design_principles.html))
- **`ERL-TEST-05`** (SHOULD) Integration tests use real Postgres (Testcontainers or docker compose) or a throw-away schema per CT suite; start the system under test with `application:ensure_all_started/1` in `init_per_suite` and stop it in `end_per_suite`. Why: Adapters need a real DB; app start is the real wiring. ([Common Test](https://www.erlang.org/doc/apps/common_test/introduction.html)) ([epgsql](https://hex.pm/packages/epgsql))
- **`ERL-TEST-06`** (MUST) Coverage: set `{cover_enabled, true}.` and `{cover_export_enabled, true}.`, add `{project_plugins, [covertool]}.`; the gate runs `rebar3 eunit --cover` and `rebar3 ct --cover`, then `rebar3 covertool generate` (Cobertura XML in `_build/test/covertool/<app>.covertool.xml`, merged by glob). Exclude generated modules with `{cover_excl_mods, [...]}` and apps with `cover_excl_apps`. Why: line coverage only; Cobertura is parseable. ([covertool](https://github.com/covertool/covertool)) ([rebar3 config](https://rebar3.org/docs/configuration/configuration/))
- **`ERL-TEST-07`** (MUST) New-code coverage: loops parses the Cobertura XML from covertool, maps files to added lines from `git diff`, requires >= 70%. Keep cover data from both EUnit and CT in `coverdata_files`. Why: Diff-cover supports Cobertura XML; native cover does not do diffs. ([covertool](https://github.com/covertool/covertool)) ([diff-cover](https://github.com/Bachmann1234/diff_cover))
- **`ERL-TEST-08`** (SHOULD) Property tests: PropEr (`?FORALL`, `proper_statem`, `proper_fsm`) via `rebar3 proper -n 500 -c`; set `{proper_opts, [{numtests, 500}]}`; use properties for pure domain functions and stateful models for gen_servers, gen_statems and ETS code. Use `proper_statem` with `parallel_commands` to hunt races. Why: Properties find edge cases; stateful PropEr is the closest thing to race testing. ([PropEr](https://github.com/proper-testing/proper)) ([rebar3_proper](https://github.com/ferd/rebar3_proper))
- **`ERL-TEST-09`** (MUST) Flakiness: no `timer:sleep` for sync (wait on a monitor or message); shuffle CT groups with `{group, g, [shuffle]}`; use a unique registered name or port per test; clock and RNG injected; `rebar3 ct --repeat N` to hunt flakes; parallel groups with `[parallel]` only for isolated tests. Why: Sleeps and shared names cause nondeterminism. ([Common Test](https://www.erlang.org/doc/apps/common_test/introduction.html)) ([rebar3 commands](https://rebar3.org/docs/commands/))
- **`ERL-TEST-10`** (SHOULD) TDD loop: `rebar3 eunit --module=m`, `rebar3 eunit --test=m:t_test`, `rebar3 ct --suite=test/x_SUITE --case=c`, `rebar3 ct --group=g`; use `rebar3 shell` plus `r3:do(eunit)`/`r3:do(compile)` (the plugin `rebar3_auto` or `rebar3_reload` for watch). Why: Single-test runs avoid the full suite; rebar3 compiles incrementally. ([rebar3 commands](https://rebar3.org/docs/commands/))
- **`ERL-TEST-11`** (SHOULD) Use `-define(TEST, true)` sparingly; guard `-ifdef(TEST).` test code in `src/` and compile with the `test` profile. Tests run in profile `test` (`_build/test`). Why: Test builds are separate from default builds. ([rebar3 ct](https://rebar3.org/docs/testing/ct/))
- **`ERL-TEST-12`** (SHOULD) Emit JUnit XML in CI with `{ct_hooks, [cth_surefire]}` in `ct_opts` and `{eunit_opts, [{report, {eunit_surefire, [{dir, "."}]}}]}`. Why: CI test reporting. ([rebar3 config](https://rebar3.org/docs/configuration/configuration/))

## PERF

- **`ERL-PERF-01`** (SHOULD) Benchmark with `erlperf` (`timer:tc/3` is too coarse) (Hex) for continuous benchmarks and compare statistically across runs. Why: `erlperf` measures throughput and concurrency. ([erlperf](https://hex.pm/packages/erlperf)) ([Efficiency guide](https://www.erlang.org/doc/system/efficiency_guide.html))
- **`ERL-PERF-02`** (SHOULD) Profile with `tprof` (OTP 27+: call time, call count, memory), `eprof`, `fprof` (heavy), `msacc` for scheduler utilisation, and `recon` in production; `observer` locally. Why: `tprof` replaces most of eprof/cprof use. ([tprof](https://www.erlang.org/doc/apps/tools/tprof.html)) ([msacc](https://www.erlang.org/doc/apps/runtime_tools/msacc.html))
- **`ERL-PERF-03`** (SHOULD) Tuning: pick scheduler flags only from measurements (`+S`, `+sbwt`, `+hms` heap size, `+P` process limit, `+Q` ports, `+zdbbl` distribution buffer); keep the JIT on (default since OTP 24 on x86-64 and aarch64). Why: Defaults are good; big changes need data. ([erl command](https://www.erlang.org/doc/apps/erts/erl_cmd.html))
- **`ERL-PERF-04`** (SHOULD) Hot-path mistakes: big messages copied between processes (pass references or use ETS), `length(L)` in guards, `lists:nth` loops, `++` accumulation, `list_to_binary` on large iolists (send iolists to the socket), non-tail-recursive loops, huge `gen_server` state copied by `process_info`. Why: Copy cost and mailbox growth dominate. ([Efficiency guide](https://www.erlang.org/doc/system/efficiency_guide.html)) ([functions](https://www.erlang.org/doc/system/eff_guide_functions.html))
- **`ERL-PERF-05`** (SHOULD) Use binary-matching patterns that keep match contexts (avoid re-creating sub-binaries in the middle) and keep binaries that outlive a request from retaining big parent binaries (`binary:copy/1`). Why: Sub-binary leaks hold memory. ([Efficiency guide: binaries](https://www.erlang.org/doc/system/binaryhandling.html))

## SEC

- **`ERL-SEC-01`** (MUST) Use parameterised queries only (`epgsql:equery/3` with `$1`, `pgo:query/2` with params); never build SQL with `io_lib:format` or `++`. Why: SQL injection. ([OWASP SQLi](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)) ([epgsql](https://hex.pm/packages/epgsql))
- **`ERL-SEC-02`** (MUST) Never call `os:cmd/1` or `open_port({spawn, ...})` with user input; use `{spawn_executable, Path}` with an `args` list. Why: Shell injection. ([EEF hardening](https://security.erlef.org/)) ([erlang module](https://www.erlang.org/doc/apps/erts/erlang.html))
- **`ERL-SEC-03`** (MUST) Decode untrusted `erlang:binary_to_term/2` only with `[safe]`, and never deserialise funs. `safe` prevents new atoms but "does not affect the deserialisation of functions and other unsafe terms", so prefer JSON, Protobuf or CBOR on the wire. Do not use `file:consult/1` on untrusted input. Why: RCE through funs, atom-table exhaustion DoS. ([EEF serialisation](https://security.erlef.org/secure_coding_and_deployment_hardening/serialisation)) ([binary_to_term/2](https://www.erlang.org/doc/apps/erts/erlang.html))
- **`ERL-SEC-04`** (MUST) Never create atoms from JSON keys or user strings: configure the JSON library to return binaries (`jsx` default is binary keys, `thoas`/`json` module keys as binaries) and validate with a schema. Why: Atom exhaustion kills the VM. ([EEF serialisation](https://security.erlef.org/secure_coding_and_deployment_hardening/serialisation)) ([jsx](https://hex.pm/packages/jsx))
- **`ERL-SEC-05`** (MUST) Distribution: a cookie is access control only (traffic is unencrypted, no MITM protection). Use TLS distribution with `{verify, verify_peer}` and mutual certs; bind EPMD and `inet_dist_use_interface` to an internal interface; never expose port 4369 or the distribution ports; do not log or commit `.erlang.cookie`; use a random cookie from the environment for releases. Why: A leaked cookie is remote code execution. ([EEF distribution](https://security.erlef.org/secure_coding_and_deployment_hardening/distribution)) ([ssl](https://www.erlang.org/doc/apps/ssl/ssl.html))
- **`ERL-SEC-06`** (MUST) Secrets come from the environment or a vault via `sys.config.src` and `vm.args.src` substitution, never from git; set `{secret, fun() -> ... end}` wrappers when logging config. Why: Configs get logged in crash dumps and `sys:get_state`. ([rebar3 releases](https://rebar3.org/docs/deployment/releases/)) ([OWASP](https://cheatsheetseries.owasp.org/))
- **`ERL-SEC-07`** (MUST) Crypto: use OTP `crypto` and `public_key` (`crypto:strong_rand_bytes/1`, never `rand` for secrets); hash passwords with Argon2id or bcrypt via a maintained NIF (for example `bcrypt` or an Argon2 NIF from Hex), never plain `crypto:hash` (SHA-2) alone. Why: `rand` is not cryptographic. ([crypto](https://www.erlang.org/doc/apps/crypto/crypto.html)) ([OWASP passwords](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html))
- **`ERL-SEC-08`** (MUST) HTTP clients and servers: enable TLS verification (`{verify, verify_peer}`, `{cacerts, public_key:cacerts_get()}` on OTP 25+, `customize_hostname_check`); validate redirects and URLs against SSRF; Cowboy needs explicit CORS and CSRF handling. Why: `ssl` defaults to verify_peer since OTP 26 but older code and `httpc` options may not. ([ssl](https://www.erlang.org/doc/apps/ssl/ssl.html)) ([OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html))
- **`ERL-SEC-09`** (MUST) Validate input at the adapter (Cowboy handler or `cowboy_rest`) with a schema library (`jesse` for JSON Schema) or pattern-matching decoders, before calling use cases. Why: Validation belongs at the edge. ([jesse](https://hex.pm/packages/jesse)) ([OWASP validation](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html))
- **`ERL-SEC-10`** (MUST) Supply chain: Hex packages have checksums recorded in `rebar.lock`; keep plugins pinned; review `rebar.config` hooks (`pre_hooks`, `provider_hooks`) in dependencies because they run shell commands at compile time. Why: Compile-time hooks execute code. ([rebar3 dependencies](https://rebar3.org/docs/configuration/dependencies/)) ([rebar3 hex](https://hexdocs.pm/rebar3_hex/))
- **`ERL-SEC-11`** (SHOULD) SAST: there is no gosec/sobelow-class Erlang tool in common use; use Dialyzer, Elvis, `rebar3_audit`, and an EEF-based Semgrep rule set where available; ELP's linter covers some diagnostics. Why: Honest gap. ([EEF Security WG](https://security.erlef.org/)) ([ELP](https://whatsapp.github.io/erlang-language-platform/))

## DATA

- **`ERL-DATA-01`** (SHOULD) Use raw SQL with a driver (`epgsql`, `pgo`; `mysql-otp` for MySQL) behind a repository behaviour; there is no dominant Erlang ORM. Mnesia, ETS and DETS are for in-memory or node-local state. Why: Keeps SQL visible and the adapter thin. ([epgsql](https://hex.pm/packages/epgsql)) ([pgo](https://hex.pm/packages/pgo))
- **`ERL-DATA-02`** (SHOULD) Migrations: keep forward-only versioned `.sql` files in `priv/migrations` and run them with a language-neutral tool (Flyway, dbmate, sqitch) or an in-app runner at release start; no migrator is dominant in Erlang. Use expand-then-contract for zero downtime. Why: Erlang lacks a standard migration framework. ([Flyway docs](https://flywaydb.org/documentation/))
- **`ERL-DATA-03`** (MUST) Transactions: begin and commit in the adapter, expose a use-case-level unit of work (a function taking a fun); keep the transaction body free of side effects. Mnesia: use `mnesia:transaction/1` and avoid dirty ops in the domain. Why: Boundary is at the use case. ([Mnesia](https://www.erlang.org/doc/apps/mnesia/mnesia.html))
- **`ERL-DATA-04`** (MUST) Connections: use a pool (`pgo` has one; `epgsql_pool`/`poolboy` otherwise), set query and checkout timeouts, size the pool to the DB, and let a crashed connection process be restarted by its supervisor. Why: Unpooled connections exhaust the DB. ([pgo](https://hex.pm/packages/pgo)) ([supervisor principles](https://www.erlang.org/doc/system/sup_princ.html))
- **`ERL-DATA-05`** (AVOID) Mnesia is not a general database: avoid network partitions (no automatic merge), limit table size (DETS 2 GB), and prefer Postgres for durable business data. Why: Split-brain risk. ([Mnesia](https://www.erlang.org/doc/apps/mnesia/mnesia.html))

## Top 10 footguns

1. **Atom exhaustion.** Bad: `binary_to_atom(Key, utf8)` or `list_to_atom/1` on request data. Fix: `binary_to_existing_atom/2` or a lookup table. ([EEF](https://security.erlef.org/secure_coding_and_deployment_hardening/serialisation))
2. **Unsafe `binary_to_term`.** Bad: `binary_to_term(Bin)` on network input. Fix: `binary_to_term(Bin, [safe])` and still never decode funs; use JSON or Protobuf. ([EEF](https://security.erlef.org/secure_coding_and_deployment_hardening/serialisation))
3. **Distribution cookie as security.** Bad: exposing EPMD (4369) and distribution ports with a default cookie. Fix: TLS distribution, bind to an internal interface. ([EEF](https://security.erlef.org/secure_coding_and_deployment_hardening/distribution))
4. **Unbounded mailbox.** Bad: a gen_server fed faster than it consumes. Fix: admission control, pools, bounded queues, `max_heap_size`, monitor `message_queue_len`. ([erlang module](https://www.erlang.org/doc/apps/erts/erlang.html))
5. **Selective receive over a large mailbox.** Bad: `receive {Ref, R} -> ...` with thousands of queued messages. Fix: use `gen_server:call` or aliases (OTP 24+ optimises receive on fresh references). ([Efficiency guide](https://www.erlang.org/doc/system/eff_guide_processes.html))
6. **Catching everything.** Bad: `try f() catch _:_ -> ok end`. Fix: let it crash or catch a specific class with the stacktrace. ([Robustness](https://www.erlang.org/doc/system/robustness.html))
7. **`gen_server:call` deadlock or default timeout.** Bad: call cycle or a call into a busy process with the 5 s default. Fix: cast, async reply, bounded timeouts. ([gen_server](https://www.erlang.org/doc/apps/stdlib/gen_server.html))
8. **Bare `spawn`.** Bad: `spawn(fun() -> work() end)` outside the supervision tree. Fix: `proc_lib` under a supervisor with a child spec. ([proc_lib](https://www.erlang.org/doc/apps/stdlib/proc_lib.html))
9. **ETS check-then-act.** Bad: `ets:lookup` then `ets:insert` from many processes. Fix: `ets:update_counter/4`, `ets:insert_new/2`, or a single owner process. ([ets](https://www.erlang.org/doc/apps/stdlib/ets.html))
10. **Sub-binary and large-message copies.** Bad: sending big terms between processes or keeping a small slice of a large binary. Fix: `binary:copy/1`, ETS or `persistent_term` for shared read-mostly data. ([Efficiency guide](https://www.erlang.org/doc/system/efficiency_guide.html))
